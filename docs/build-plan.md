# Build plan (working document)

The live status, the next steps and the working agreement for whoever is building
this next, human or agent. `docs/plan.md` is the agreed scope and design; this file
says where the build is, what to do next and how to do it. Update it in the same PR
as the work, so it never drifts: move the item, add the decision, close the question.

Read in this order: `CLAUDE.md` (rules), this file, then the sections of
`docs/plan.md` your item names. `README.md` covers running the app.

**How to add a recurring job (4A).** Jobs that must not be missed (auto-close, chase, approval reminders, later the MSP
handoff) go in the `scheduled_job` table, not in `app/jobs`. It is a one-place change:
1. Write the function in its own module: `def my_job(session: Session) -> None`. Do the work on the session it is given and do
   not commit (the runner commits on return and rolls everything back if it raises). Work out what is due from ticket data
   ("tickets chased more than N days ago"), not from "since the last run": the job may run late, once, and after a crash twice.
2. Add one line to `SCHEDULED_JOBS` in `app/scheduled_jobs.py`: `ScheduledJobDef("approval-reminders", 3600, my_job)`
   (name, interval in seconds, function). No migration and no worker edit: the row is created on the next tick, due at once.
3. Test it by calling the function with a test session for the logic, and `run_due_jobs([job], "w1", clock)` with a fake
   clock (see `tests/test_scheduled_jobs.py`) for scheduling. Tunable values are admin settings as usual.
Behaviour to know: the worker ticks every minute; a job overdue by more than the late setting (default 3 minutes) runs once and
writes an audit line "Job x ran late"; a failure is stored (Admin > Recurring jobs), rolled back and retried after the retry setting
(default 5 minutes, never longer than the job's interval); a worker that dies mid-run leaves a lease that expires after the lease
setting (default 10 minutes, set it longer than the slowest job) and the job then runs again. Each run logs the usual
`heartbeat job=<name> status=ok` line, or `job=<name> status=failed` with the traceback.

**Resolve action (4D, built).** `app/resolution.py` is the one place a ticket becomes Resolved; `set_status` raises `ResolutionRequired` for Resolved unless called with `by_resolution=True`. Later issues call `resolve_ticket(session, ticket, actor, notes, cc_emails=None, send_email=True, detail=None)`: 4E-1 (reopen) adds to `reopen_count` and clears the notes if it wants to; 4F puts the reopen and feedback links into the `resolution` template; 4H passes `actor=None` and `auto_resolution_note(session, ticket, days)` (template key `auto_resolve_note`); 4I loops it over linked tickets. `preview_resolution` is the "are you sure?" step (it reuses `preview_email`). Failures are `ResolveError` (a bad copy address is `UnknownRecipient`), raised before anything changes. Decisions: (1) the resolution email is an ordinary agent email (kind `reply`, counts as a first response, copies followers by the same tick list as Email user) and an automatic resolve is a `notice` that copies every follower; (2) a ticket raised already resolved (`app/raising.py`) needs resolution notes (new form field) and sends no resolution email, since it is logged after the fact; (3) `closed_at` is set by `set_status` whenever the status becomes Closed and cleared when it leaves Closed, and `resolved_at` keeps its existing rules; (4) leaving Resolved or Closed for an open status clears `resolution_notes` and `resolved_by_id` in `set_status` (the timeline, the audit entry and the email keep what was said), so a reopened ticket never shows a stale resolution; `reopen_count` is only the column for now, 4E-1 increments it; `resolve_ticket` row-locks the ticket and re-reads it before checking, so a double submit gives one email; (5) closing a ticket directly (Open to Closed) stays allowed and needs no notes; (6) the audit entry is `ticket` / `resolved` with the first 200 characters of the notes, written by the helper, `system` as actor for an automatic resolve; (7) the notes are put into the template as a value, so braces in them stay as written.

**Auto-close and chase (4H, built; migration `5d1f0c2b7a96`).** `app/auto_close_chase.py`, two jobs (`auto-close`, `chase`, hourly). Decisions: (1) **both switches are off by default** (`auto_close_enabled`, `chase_enabled`) until mail is proved on staging; settings `auto_close_after_days` 7, `chase_after_days` 3, `chase_resolve_after_days` 3 are placeholders. (2) The chase is its own outbox kind, `chase`, built by `mail.build_chase_mail` from the admin template `chase` under the ticket's own `[INC-n]` subject (a part of a split request gets the "About:" line); it joins `AUTOMATIC_TO_REQUESTER`, so it shares the per-ticket cap with notices and receipts. It is asked again when sent: the ticket must still be Awaiting user and still chased, else it is dropped (`Unsendable`), so a reply that lands while it is queued or held stops it. It is an event (`chased`) and audit entry for agents, not a timeline message to the requester. (3) The wait starts at the ticket's latest status change to Awaiting user (the status events), not at its age, so a ticket that leaves and comes back starts again. (4) Cancelling: `set_status` clears `chased_at` and `chase_count` on any move out of Awaiting user, which covers a mailed or portal reply (`apply_requester_reply`), an agent's change and a reopen; nothing else needs to know about chasing. The emailed reopen link only applies to Resolved tickets, and reopening an auto-resolved ticket goes through `reopen_ticket`, which leaves Awaiting user's chase state already cleared. (5) Auto-resolve counts Y days from when the chase email was **sent** (`outbox.sent_at`), so a chase held by the cap or by mail being down does not run the clock; a chase that was given up on is never followed by an auto-resolve (an agent decides). With `MAIL_SENDING=off` nothing is newly chased, but a ticket already chased is still resolved when due. (6) Only Awaiting user is chased, so With supplier and With MSP are excluded by construction (and a test says so). A split original (anything with sub-tickets) is never chased or auto-resolved itself: its parts are, one by one, and its derived status follows. (7) Auto-close: `resolved_at` older than N days, Resolved only; a reopen clears `resolved_at`, so a re-resolved ticket starts its N days again; status change uses `set_status(Closed, actor None, detail "auto-closed")` plus an `auto_closed` event and an audit entry by `system`; a split original with unfinished parts is skipped. (8) Both jobs lock each ticket with `FOR UPDATE SKIP LOCKED` (its original first, for a part) and re-check under the lock, so a ticket an agent is working on is left to the next run and the job never waits. (9) The auto-resolve note says "after N days" where N is the whole days since it started waiting (at least 1), not the settings. (10) The chase goes to the requester only; the auto-resolve's resolution email copies every follower, as the 4D decision says.

**Out-of-office lookup bookkeeping (4B-4, built; migration `a3483204f1e2`).** `User.last_presence_lookup_at` is a new column, not a rename: `out_of_office_checked_at` stays the time of the last good reading (the three-hour staleness rule needs it). Hiding inactive people from pickers, refusing their sign-in and the nightly Entra `accountEnabled` check that sets it are Phase 6 (build once, this flag).

**Follower updates (4B-6, built).** When the requester or a follower adds to a ticket, by email (`ingest_mail`, reply branch) or in the portal (`/portal/{n}/comment`), `follower_updates.queue_follower_updates` queues one `follower_update` email per person who was not already sent it. Who is decided only in `followers.uncopied_recipients`: the external followers, plus the requester when the sender is not the requester, minus the sender, the To and Cc of the mail (compared as lower-case bare addresses, so `Pat Smith <PAT@x.org>` equals `pat@x.org`; `followers.bare_address`), the shared mailbox and any never-follow address. Internal (agent) followers are not emailed; they are told in the bell and Teams as before. `InboundMail` now keeps `to_addresses` and `cc_addresses`; `OutboundEmail.about_message_id` names the inbound message being passed on, unique with `to_address`, so a replay or a second call queues nothing. `mail.build_follower_update_mail` asks again at send time: triaged (else it waits like any reply), the message is one `requester_visible_messages` returns, the person still follows (or is the requester), is not newly listed, and has not turned off the new "A ticket you follow is updated by someone else" email setting (`notification_settings.FOLLOWER_UPDATE`, default on; people without an account are always told). Wording is the `follower_update` template (subject is the ticket's own, `{sender}` and `{message_text}` are the placeholders). The automatic-email cap for this kind is its own allowance, counted per recipient, so a chatty follower cannot hold back the requester's notices. Also fixes a gap from 4B-2: `messages._copied_followers` (agent Email user, preview, resolution email) now uses the same `followers.copyable_followers` as `cc_list`, so a follower listed after following is never copied, and the tick list (`followers.copyable_followers`) does not offer them. Decision: portal comments update followers by the same rule and function (copied list empty), recorded 21 Oct 2026. Not built: the mail that opens a ticket (those Cc'd are followers and have it already), and reply-all Cc'd strangers are still not made followers.

**Acknowledgement email (4B-3, built).** A ticket opened by a person's email gets one automatic receipt, queued by `outbox.queue_acknowledgement` (kind `acknowledgement`) from `ingest_mail` after the ticket is created, built by `mail.build_acknowledgement_mail`, wording in the `acknowledgement` template (`app/email_templates.py`; body only, placeholders `{reference}` and `{ticket_number}`, so an admin cannot put ticket content in it). It is the one deliberate exception to "no requester email before triage": it waits for nothing and carries no ticket content, no queue position and no promised time (an emailed ticket has no priority until triage). It goes under the ticket's own `[INC-n] subject`, as automatic mail (`X-Auto-Response-Suppress`), counts toward the per-ticket automatic cap (held, not lost) and never goes to the shared mailbox. Never queued for automatic mail, bounces, our own mail, drafts, a flood or a sender with no usable address (all settled before a ticket exists), nor for a sender on the never-follow list (a list or shared mailbox would only answer back). Once per ticket is checked in `queue_acknowledgement` (no migration). Tickets raised in the portal or by an agent get none (they see it on screen, or get the raised-for-you email). **Mail intake seam (3C, for 3B).** `app/subscriptions.py` owns keeping mail arriving; 3B owns turning it into tickets.
- The webhook (3A) and the catch-up both end the same way: a `GraphNotification` row with `resource_id` = the Graph message id and
  `processed_at` NULL. 3B's job processes rows where `lifecycle_event IS NULL`. **Rows with a `lifecycle_event` belong to 3C**
  (`graph-subscription` job marks them processed); 3B must skip them.
- The catch-up (`catch_up`, job `mail-catch-up`, every 5 minutes) hands ids to a `MailIntake` callable
  `(session, message_ids, source) -> new count`. The default `record_for_processing` inserts a `GraphNotification` row for each id
  that has no row yet (any state), so 3B needs no code change; it dedupes on `resource_id`, and 3B's unique `internetMessageId` is
  the backstop (a webhook and a catch-up can race and write two rows for one id). If 3B wants a different hand-over it passes its own
  function to `catch_up(intake=...)`.
- **Race to be aware of:** a webhook and a catch-up run can both insert a `GraphNotification` row for one message id (the table has
  no unique constraint on `resource_id`, so the webhook stays a plain insert inside Graph's 3 seconds). Two rows must never mean
  two tickets: 3B's processing has to be idempotent per message, with the unique constraint on the message's `internetMessageId`
  (and the Graph message id) as the backstop, and the second row simply marked processed.
- Switches (worker env, all off by default): `GRAPH_SUBSCRIPTION_ENABLED` + `GRAPH_NOTIFICATION_URL` (public https address of the
  webhook, also the lifecycle address), `MAIL_CATCH_UP_ENABLED` (polling only, needs no public URL). Settings: subscription lifetime
  (10000 min, capped at 10070), renew margin (1440 min), backfill days (3). The very first catch-up run does not look back: it takes the delta from now to its end,
  stores the deltaLink and the starting point (`MailSyncState.starting_point_at`) and hands nothing over, so existing inbox mail is
  never imported. Backfill days apply only to a restart after Graph answers 410. `/health` stays 200 and adds `warnings` when the subscription is near expiry, expired, or a
  check failed. 3F: pass the three env vars to the worker (Bicep not touched here).

## Invariants (where rules live)

- **Cross-site protection is `SameSite=Lax` on the session cookie** (`app/main.py`), not per-form
  tokens. Browsers do not send that cookie on a cross-site POST, which is what keeps another site
  from submitting our forms as the signed-in person (for example "untick everything" on the
  notification settings). A test pins the setting. Anything that would weaken it (`SameSite=None`, an
  embedded or cross-site login flow) needs form tokens first.

- **Access** is decided only in `app/visibility.py` and comes from the ticket's
  team: member works, viewer reads. Assignee, triager, escalator and follower grant
  nothing. The exceptions are the shared untriaged queue and a parent
  team's view of its sub-teams, and the escalator's access to the one ticket they
  escalated (`TicketEscalator`). `visible_ticket_condition`
  is the SQL twin of `ticket_access`; a test keeps them in step. Get what a user can
  reach only from `access_context(session, user)`: it loads once per database session and
  is dropped on every flush, commit and rollback, so never build or keep your own copy.
- **What the requester sees** and whether a ticket can be emailed: only
  `app/messages.py` (`requester_visible_messages`, never `ticket.messages`).
- **Ticket numbers**: one shared counter, never change. `reference` (INC-12) is a
  display property that follows the type. Routes and links use the number. Look
  tickets up with `find_ticket` / `get_by_number`. Stored history uses `ticket.tag`
  (`#12`), because the prefix can change.
- **Triage** is separate from assignment; a ticket leaves New only by triage.
- **SLA**: deadlines are fixed when set (triage, priority change, end of a pause)
  and changed targets never touch existing tickets. Targets are settings with
  placeholder values. Backdated tickets have no SLA.
- **Settings, not constants**, for anything marked TBC in the plan.
- Frontend is server-rendered Jinja2 and htmx, plain HTML. The Stitch redesign is
  phase 9, so no styling effort now. 4xx errors reach htmx through the global
  handlers into `#flash`.
- Every state-changing action writes a ticket event and an audit entry, and nothing
  in the service functions commits; the route commits.
